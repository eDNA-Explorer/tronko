# Golden output provenance

Reference output for `ancestralclust/test_consistency.sh`.

## How to regenerate

From the repository root, with `ancestralclust/ancestralclust` freshly built:

```bash
ancestralclust/ancestralclust -f -u \
    -i tronko-build/example_datasets/single_tree/Charadriiformes.fasta \
    -b 50 -r 100 -p 10 -c 1 \
    -d ancestralclust/test_data/golden_output
```

`-c 1` is required: single-threaded, with `srand(42)` fixed, the run is fully
deterministic and repeat runs are byte-identical.

## Regenerated 2026-08-19

Replaces a golden produced before commit `ca8336b`. That earlier golden was
complete (all 1,466 input sequences) but was generated by code that read
`assignedReads[kseqs]` out of bounds; the resulting heap-garbage comparison
influenced which records were admitted, and therefore the clustering. It is not
a reference any correct build can reproduce.

The current golden was produced by the build that fixes two data-loss bugs in
`readInXNumberOfLines` (seed-exhaustion treated as end-of-data, and an `iter`
desync at chunk boundaries). Both goldens cover **exactly the same 1,466
sequences** — the only difference is the partitioning, 13 clusters before
versus 16 now.

Validated before installation:

| property | result |
|---|---|
| input sequences | 1,466 |
| records written | 1,466 |
| distinct accessions | 1,466 |
| missing | 0 |
| duplicated | 0 |
| sequence-set difference vs old golden | 0 |
| byte-identical across repeat runs | yes |

## Why the test does not rely on this alone

A golden diff cannot distinguish "the clustering changed" from "sequences were
lost", and that blind spot is how a silent truncation shipped: on real markers
it removed up to 11% of the reference, and on one it took 128 species to zero
representation. `test_consistency.sh` therefore also asserts, independently of
this directory, that every input accession appears exactly once across the
output clusters. If you regenerate the golden, that assertion is what still
protects you — keep it.
